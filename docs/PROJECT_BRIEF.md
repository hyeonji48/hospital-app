# 부천시 혁신나래연구단 해커톤 — 병원 내비게이션 서비스 프로젝트 브리핑

> 새로운 세션이 이 프로젝트의 맥락을 처음부터 파악하기 위한 인수인계 문서.
> 최종 갱신: 2026-08-23 (대회 계보·대상 병원·브랜딩 확정 반영)

## 0. 한 문단 요약

가톨릭대학교 학생 팀이 **부천시 혁신나래연구단 해커톤**에 출전한다. 제안하는 것은 **병원 서비스
정책**이며, 구체적으로는 **가톨릭대학교 부천성모병원을 시범 대상으로 한 병원 내 동선 안내
서비스**다. 이미 프로토타입이 존재하고 목데이터가 들어가 있다. 지금 해야 할 일은 **그 목데이터를
부천성모병원의 실제 층별 구조 데이터로 교체하고, 심사에서 설득력 있는 시연 동선을 설계하는 것**이다.

## 1. 대회 정보와 평가 기준 (가장 중요 — 모든 판단의 기준)

**현재 출전 대회: 부천시 혁신나래연구단** (과제명: 혁신나래연구단 연구과제 / 총점 100점)

**대회 계보 (혼동 주의):**

| 단계 | 대회 | 상태 |
|---|---|---|
| 이전 | 제1기 CUK 지속가능사회 청년리더 양성 프로그램 (부천시 정책 제안서) | **완료** — `정책제안서_양식.pdf`, `동행온 예선용.pdf` |
| **현재** | **부천시 혁신나래연구단** | **출전 예정** — `동행온 본선 발표용 피치덱.pdf` |

CUK에서 만든 제안을 **디벨롭**하고, 여기에 **부천시 공무원과 직접 논의한 내용**을 반영해
혁신나래연구단에 정책 제안하는 구조다. 두 대회는 단절이 아니라 연속이다.

→ **"공무원과 직접 논의했다"는 사실은 충실성 참여도 15점의 강력한 증빙이다.** 논의 일시·참석자·
   논의 내용을 반드시 기록해 발표자료 부록에 편성할 것.

| 항목 | 세부항목 | 배점 | 평가 내용 |
|---|---|---:|---|
| **활용가능성 (40)** | 실현가능성 | 15 | 부천시에서 시범사업 등 실제 추진이 가능한 제안인가? |
| | 확장성 | 15 | 일회성 사업이 아닌 향후 확장 가능성이 있는가? |
| | 공공성 | 10 | 특정 집단이 아닌 다수 시민에게 도움이 되는 제안인가? |
| **창의성 (30)** | 독창성 | 15 | 기존 정책과 다른 새로운 아이디어인가? |
| | 참신성 | 15 | 문제를 해결하는 방법이 창의적이고 참신한가? |
| **충실성 (30)** | 참여도 | 15 | 연구과정 및 모임 활동에 성실히 참여하였는가? |
| | 완성도 | 15 | 제안이 논리적이고 접근방법이 충실하게 제시되었는가? |

**전략적 함의:**

1. **"부천시에서"라는 단어가 실현가능성 15점의 핵심.** 대상 기관은 반드시 부천시 소재여야 한다.
2. **확장성 15점은 기술 아키텍처로 증명 가능하다.** 데이터와 엔진을 분리한 구조 자체가 답변 근거.
3. **공공성 10점은 프레이밍 문제.** 병원 한 곳짜리 앱은 "특정 집단"으로 읽힐 위험이 있다.
4. **창의성 30점이 최대 리스크.** 병원 실내 내비게이션은 이미 대형병원들이 하고 있어 "기존에 있는
   것 아니냐"는 반론에 취약하다. 차별화 축이 반드시 필요하다.
5. **충실성의 참여도 15점은 아이디어가 아니라 기록으로 채점된다.** 회의록·현장답사 사진·인터뷰·
   커밋 로그가 곧 점수다.

## 3. 확정된 핵심 결정사항

### 3.1 대상 기관 = 가톨릭대학교 **부천성모병원** (서울성모 아님)

평가 첫 항목이 "부천시에서 추진 가능한가"이므로, 서울성모·은평성모 등으로 만들면 실현가능성
15점이 소멸한다.

**부천성모병원 팩트 (발표자료 사용 가능):**

- 주소: **경기도 부천시 원미구 소사로 327** (14647)
  ※ 병원 공식 홈페이지 표기가 **원미구**다. 이전 자료의 '소사구' 표기는 정정할 것.
- 규모: 624~630병상 (일반 584, 중환자 58, 응급 38)
- 진료 규모: 30개 진료과, 46개 클리닉, 10개 전문진료센터
- 대지면적 15,255.25㎡ / 건평 39,680.99㎡
- 부천시 최초의 대학병원. 부천 내 순천향대부천병원에 이어 두 번째 규모
- 연혁: 1958년 성가의원 → 1983년 부천 소사동 이전 → 2009년 부천성모병원으로 개칭
- 첫 방문 환자는 **본관 1층 초진창구**를 먼저 방문 (동선 설계의 시작점)
- 국제의료원 운영 (영어·러시아어, CIS권 환자 대응) → 다국어 기능의 논거

**전략적 이점:** "부천시 소재 + 가톨릭대와 동일 재단 + 팀이 가톨릭대 소속" → 시범사업 MOU 서사가
억지 없이 성립한다.

### ✅ 프로토타입 대상 확정 (2026-08-23)

**부천성모병원 약도 기반으로 프로토타입을 제작한다.** 실제 층별 구성은
`docs/BUCHEON_CMC_FLOORS.md` 참조 (공식 홈페이지 `병원둘러보기`에서 수집).

- 1차 구현 범위: **성모관 1F + 2F**
  → 예선덱의 AI 변환 예시 시나리오(내과 접수 → 채혈실 → X-ray → 내과 대기)가
    이 2개 층 안에서 **전부 성립한다.** 브리핑 §7의 "3개 층" 예산보다도 작다.
- 나머지 층(B1·3F·4F) 및 성가정관·성심관은 "동일 스키마로 확장 예정" 처리

⚠️ **`정책제안서_양식.pdf` p5의 4개 후보 병원 리스트는 현재 방침과 어긋난다.**
(부천시립노인전문병원 / 근로복지공단 인천병원 / 순천향대부천병원 / 부천성모병원)
특히 **근로복지공단 인천병원은 인천 소재**라 "부천시에서 추진 가능한가"(실현가능성 15점)에서
역공당할 수 있다. 혁신나래 제출본에서는 **부천성모 단일 시범 + 나머지는 확장 로드맵**으로
정리할 것.

### 3.2 시연용/실서비스는 "앱 두 개"가 아니라 "데이터 레이어 한 겹"으로 분리

```
[UI / 라우팅 엔진]   ← 코드베이스는 하나만 존재
        ↑
[데이터 어댑터 인터페이스]
        ↑
 bucheon-cmc.json (부천성모 실측)  |  demo-scenario.json (시연 고정값)
```

**이유 1 (실무):** 해커톤 기간에 두 개의 프로덕트를 유지보수하면 둘 다 반쯤 망가진 채 끝난다.
**이유 2 (점수):** "그거 목데이터 아니에요?" 질문이 오히려 기회가 된다. 준비된 답변:

> "라우팅 엔진과 데이터를 분리했습니다. 지금 보신 건 부천성모 본관 실측 데이터고, 다른 병원은
> 층별안내도만 있으면 동일 스키마로 반나절 안에 온보딩됩니다."

이 한 문장이 **확장성 15점**을 확보한다. 목데이터 → 실데이터 교체 작업 자체가 확장성의 증거물이
된다. 이 과정("범용 스키마 → 부천성모 인스턴스 → N개 병원 확장")을 슬라이드 한 장으로 반드시 제작.

### 3.3 공공성 방어: "부천성모병원 앱"이 아니라 "부천형 의료접근성 표준"

병원 한 곳 대상이면 특정 집단으로 읽힌다. 포지셔닝을 상위 레이어로 올리고 부천성모를 1호
시범기관으로 둔다. 확장 로드맵에 순천향대부천병원, 부천세종병원, 부천시 보건소를 포함시켜
공공성 10점 + 확장성 15점을 동시에 방어한다.

## 4. 창의성 30점 확보를 위한 차별화 축 (✅ 2026-08-23 결정)

### 문제 인식

병원 실내 내비게이션 앱은 서울아산·삼성서울 등이 이미 제공 중. 단순 길찾기로 가면 독창성 15점 +
참신성 15점이 크게 깎인다. 차별화 축이 반드시 필요하다.

### ❌ 폐기: "최소 체류시간 순서 최적화" 스케줄러

당초 제안했던 축(채혈실이 붐비면 영상검사를 먼저 배치하는 스케줄러)은 **2026-08-23 팀 결정으로
채택하지 않는다.** 개발 범위 증가 대비 이득이 불확실하다는 판단.

### ✅ 채택: "목적지를 검색하지 않는 내비게이션" — 접수증 기반 안내

키오스크에서 예약·접수하면 **접수증에 오늘 할 일이 순서대로 인쇄되어 나온다.**
환자는 그 종이를 찍기만 하고, 앱이 그 목록을 따라 순차적으로 길을 안내한다.

**핵심 논거 — 기존 앱이 푸는 문제와 안 푸는 문제:**

| 환자가 헤매는 이유 | 기존 병원 앱 |
|---|---|
| (a) 길을 모른다 | 푼다 — 단, **목적지 이름을 검색창에 입력할 수 있어야** |
| (b) **어디로 가야 하는지, 몇 개를 해야 하는지 모른다** | **아무도 안 푼다** |

기존 앱은 "정형외과"를 검색할 줄 아는 사람용이다. 그런데 그걸 아는 사람은 애초에 덜 헤맨다.
**접수증에는 답이 이미 전부 적혀 있는데, 그것을 읽고 순서대로 따라가는 것을 못 하는 것이
진짜 문제다.**

> **한 줄 메시지: "접수증이 곧 경로가 됩니다. 검색할 필요가 없습니다."**

**이 축의 강점 두 가지:**

1. **억지가 없다.** 기존 프로토타입이 정확히 이 구조다 (`CameraView` → `ConfirmScreen` →
   태스크 순차 안내). 콘셉트에 맞춰 코드를 새로 짜는 게 아니라 **코드가 이미 주장의 증거물**이다.
2. **확장성 논거로 재사용된다.** "병원마다 접수증 양식만 매핑하면 온보딩" → §3.2 데이터 레이어
   서사와 그대로 결합. 확장성 15점을 두 번 방어한다.

**데이터 모델 분리:**

```
접수증  →  "무엇을 할지" (태스크 목록·순서)
그래프  →  "어떻게 갈지" (경로)
```

기존 `TASKS: Task[]`가 그대로 "접수증 파싱 결과"에 대응한다. 구조 변경이 거의 없다.

### ✅ 2026-08-24 결정: 실제 구동 + 자체 제작 샘플 접수증

팀 회의 결과 **실제 병원에서 앱을 구동해보는 방향**으로 확정. 다만 촬영 대상은
**실제 환자 접수증이 아니라 자체 제작한 샘플**(`public/sample-receipt.html`)이다.

이 선택이 세 가지를 동시에 해결한다:

1. **개인정보** — 실제 환자 이름·생년월일이 외부로 나가지 않는다.
2. **무료 티어 사용 가능** — Gemini 무료 티어는 입력이 학습에 쓰이지만, 가상 데이터라 무해하다.
   예산 0원으로 개발·시연이 가능해진다.
3. **인쇄 품질 통제** — 감열지 흐림 문제 없이 안정적으로 인식된다.

**심사 답변으로 정리해 둘 것:**

> "개발·시연 단계에서는 실제 환자 정보를 일절 사용하지 않았습니다. 자체 제작 샘플
> 안내문으로만 검증했고, 실제 시범사업 단계에서는 유료 티어로 전환해 입력 데이터가
> 학습에 사용되지 않도록 합니다."

개인정보 질문에 준비된 답이 생긴다 → **완성도 15점.**

### ⚠️ 접수증 스캔이 아직 UI에 붙지 않았다

`CameraView`는 실제 카메라를 켜지만 "촬영" 버튼은 `setTimeout(1800)` 후 다음 화면으로 넘어갈
뿐이다. OCR이 없다. 아무 종이나 들이대도 통과한다.

축이 바뀌기 전에는 부차적 문제였으나, **이제 접수증 스캔은 핵심 주장의 유일한 증거물이다.**
"검색이 필요 없습니다"라고 말하는 순간 심사위원의 시선이 그 장면에 꽂힌다.

→ **최소한 실제 접수증 1장은 진짜로 인식되어야 한다.**

**구현 방식 (확정):** 별도 OCR 서비스를 쓰지 않고 **Gemini가 사진을 직접 읽는다.**
붙일 서비스가 하나 줄고, 실패 지점이 하나 줄고, 배치 정보까지 보므로 정확도도 유리하다.
발표에서는 "AI가 사진을 읽습니다"로 설명하면 되고, 덱의 OCR 서술도 크게 바꿀 필요 없다.

서버 `api/transform.ts` 가 이미 사진 입력을 받는다. 남은 것은 UI 배선.

### 보조 축 (여력이 있을 때)

- **타깃 페르소나: 보호자 없이 방문하는 고령 환자.** 부천시 고령화 추세와 연결.
- **병원 밖까지 확장:** 버스정류장 → 병원 정문 → 진료실의 seamless 연결. 부천시 교통 데이터와
  결합하면 "부천시 사업"이라는 성격이 강해진다.

## 5. AI 사용 범위

### 쓸 것

- **자연어 입력 → 목적지 매핑.** "어머니 모시고 심장 쪽 검사 왔는데요" → 순환기내과 + 심전도실.
  어르신이 진료과 이름을 모르는 것이 실제 문제이므로 임팩트가 크다.
- **검사 순서 추천 사유의 자연어 설명.** "지금 채혈실이 붐벼서 영상검사를 먼저 하시는 게 20분 빠릅니다."
- **다국어 안내.** 부천은 외국인 주민 비율이 높고, 부천성모에 국제의료원이 있다는 사실이 논거.

### 쓰지 말 것 (중요)

- **경로 계산 자체를 LLM에게 시키지 말 것.** 경로는 결정론적 그래프 탐색(Dijkstra / A*)이어야
  한다. LLM에 맡기면 존재하지 않는 복도를 생성하며, 하필 시연 중에 그런 일이 발생한다.
- **원칙: 경로는 결정론적으로, 말은 LLM으로.**
- 시연 시 LLM 호출 결과를 사전 캐싱하고, 타임아웃 시 폴백 문구 표시. 네트워크는 항상 배신한다.

## 6. 데이터 스키마 (초안)

```json
{
  "hospital": { "id": "cmc-bucheon", "name": "가톨릭대학교 부천성모병원" },
  "nodes": [
    { "id": "b1-lobby", "floor": 1, "x": 320, "y": 180,
      "type": "landmark", "name": "본관 1층 로비" },
    { "id": "b1-reception", "floor": 1, "x": 400, "y": 210,
      "type": "desk", "name": "초진창구", "dept": null },
    { "id": "b1-elev-a", "floor": 1, "x": 500, "y": 150,
      "type": "elevator", "group": "elev-a" }
  ],
  "edges": [
    { "from": "b1-lobby", "to": "b1-reception",
      "dist": 18, "mode": "walk", "accessible": true },
    { "from": "b1-elev-a", "to": "b2-elev-a",
      "dist": 0, "mode": "elevator", "cost": 45, "accessible": true }
  ]
}
```

**설계 포인트:**

1. 엘리베이터/계단을 노드로 두고 층간 이동을 edge로 표현하면, 3D 좌표 없이도 다층 라우팅이 성립.
2. `accessible` 플래그로 계단 edge를 제외하면 그것이 곧 휠체어·유모차 모드다. 코드 몇 줄로
   공공성 근거가 하나 생긴다.
3. 가중치 = 거리 + 층이동 페널티 + (모드별 추가 페널티). 페널티 테이블만 교체하면 고령자 모드,
   휠체어 모드 등 여러 페르소나가 파생된다.

**노드 타입 후보:** `room`(진료실/검사실), `desk`(창구), `corridor`(복도 분기점), `elevator`,
`stairs`, `entrance`, `landmark`

## 7. 구현 범위 — 의도적으로 좁게

**전 층을 다 만들려다 아무것도 못 끝내는 것이 가장 흔한 실패다.**

- 권장 범위: **본관 지하1층 · 1층 · 2층, 노드 40~60개**
- 나머지 층은 "동일 스키마로 확장 예정"으로 처리
- 대신 만드는 3개 층은 좌표까지 정확하게

**렌더링 방침:**

- 층별안내도를 SVG로 트레이싱하고 노드 좌표를 같은 viewBox에 정렬
- **병원 공식 도면 이미지를 발표자료에 그대로 사용하지 말 것** (저작권상 애매). 단순화한 자체
  SVG로 다시 그린다. 어차피 실제 도면보다 단순화한 쪽이 화면 가독성이 높다.

## 8. 데이터 수집 실행 계획 (팀 총출동, 반나절)

0. **★최우선: 실제 접수증 실물 확보 + QR·바코드 인쇄 여부 확인.** §4의 리스크가 여기서
   해소되거나 확대된다. 이것 없이 스캔 기능 개발을 시작하지 말 것.
1. 병원 홈페이지 `병원안내 > 층별안내` 도면 확보
2. **현장 답사:** 각 층 사진 촬영, 엘리베이터·계단·경사로 위치 기록, 구간별 **걸음 수로 거리 추정**
3. **인터뷰:** 원무과 직원 / 자원봉사자에게 "환자들이 제일 많이 헤매는 곳이 어디인가" 질문
4. **스톱워치로 실제 체류시간 측정** → 발표용 Before 숫자 확보

이 활동에서 나온 사진·회의록·인터뷰 메모를 **절대 버리지 말고 발표자료 부록에 편성할 것.**
충실성 항목의 참여도 15점은 이 기록물로 채점된다.

## 9. 시연 설계

**시나리오는 딱 하나만, 대신 아주 정교하게.** 여러 개를 보여주면 전부 흐려진다.

```
78세 김OO 어르신 / 첫 방문 / 순환기내과 초진 + 채혈 + 심전도
정문 진입
  → "심장 쪽 보러 왔어요" 음성 입력
  → 본관 1층 초진창구 안내
  → 검사 순서 자동 배치
  → 층별 경로 안내
  → 수납 · 약국까지 완주
기존 체류 84분 → 51분 (팀 실측 기준)
```

- 목표 길이: **90초**
- Before/After 숫자가 발표 전체에서 가장 오래 기억에 남는다. 그래서 8번의 실측이 중요하다.
  (84분/51분은 예시 수치이며 **실측값으로 반드시 교체할 것.**)
- 시연 중 네트워크 및 실시간 API 의존을 최소화할 것.

## 11. 새 세션이 이 문서를 읽었을 때 취해야 할 태도

- 사용자는 **설계와 개발을 함께 논의하는 것**을 원한다. 결론만 던지지 말고 근거와 트레이드오프를
  같이 제시할 것.
- 사용자의 초안에 위험이 있으면 **직접적으로 지적할 것.** (예: "시연용/실서비스 두 개 만들기"는
  그대로 두면 위험하다고 판단해 구조를 바꿔 제안했고, 사용자가 수용했다.)
- **모든 제안은 평가기준표의 어느 항목 몇 점에 대응하는지와 함께 설명할 것.** 이것이 이 프로젝트의
  일관된 판단 기준이다.
- 개발 범위 확장 제안 시에는 항상 **잔여 기간 대비 리스크를 함께** 말할 것. 해커톤이므로
  "완성하지 못하는 것"이 가장 큰 실패다.
